# Topic Analysis System — Design Specification

**Package:** `Sigyn/scripts/topic_analysis/`  
**Status:** Implemented  
**Audience:** Developers extending or maintaining this pipeline; authors using it as a reference for the *ROS 2 for Mere Mortals* book series  

---

## 1. Purpose and Motivation

A ROS 2 robot at the complexity level of Sigyn publishes 100+ topics from a heterogeneous hardware stack: Teensy microcontrollers, lidars, depth cameras, a differential-drive motor controller, Nav2, and multiple behavior trees. Without a systematic inventory, it becomes difficult to answer basic questions:

- Which topics are consuming the most bandwidth?
- Is the IMU publishing at 100 Hz as expected?
- What does `/sigyn/safety/state` actually contain?
- Which topics have no subscribers? (dead code?)
- Which topics have publishers but never sent a message during this run?

The topic-analysis pipeline answers all of these questions in three steps:

1. **Gather** — subscribe to every live topic in parallel, measure Hz, bandwidth, and end-to-end delay
2. **Describe** — merge a human-written description database with the measured data
3. **Report** — render a rich, navigable Markdown document

The steps are deliberately separated so that the slow data-gathering step does not need to be repeated when only the report format or descriptions change.

## 2. Architecture

```
┌──────────────────────────────────────────────────────────────────┐
│                          run_all.py                              │
│           (convenience wrapper — calls all three steps)          │
└──────────────┬──────────────────────────────────────────────────┘
               │
    ┌──────────▼──────────┐
    │      gather.py       │  reads:  live ROS 2 topics (rclpy)
    │   (rclpy node)       │          sample_durations.json
    │                      │  writes: topic_data.json
    │                      │          sample_durations.json (updated)
    └──────────┬──────────┘
               │
    ┌──────────▼──────────┐
    │     describe.py      │  reads:  topic_data.json
    │  (pure Python, no    │          topic_descriptions.json
    │   ROS required)      │  writes: topic_data_described.json
    └──────────┬──────────┘
               │
    ┌──────────▼──────────┐
    │      report.py       │  reads:  topic_data_described.json
    │  (pure Python, no    │          sample_durations.json (for health)
    │   ROS required)      │  writes: topic_analysis.md
    └─────────────────────┘
```

Only `gather.py` requires a running ROS 2 environment (`rclpy`). The remaining steps are pure Python and can be run on any machine that has the JSON files.

## 3. File Inventory

### Scripts

| File | Role |
|------|------|
| `gather.py` | ROS 2 node — discovers topics, parallel-subscribes, measures Hz/BW/delay, writes JSON |
| `describe.py` | Merges description database with gathered data |
| `report.py` | Renders Markdown report from described data |
| `run_all.py` | Convenience wrapper that chains all three steps |

### Data Files (version-controlled)

| File | Role | Overwrite policy |
|------|------|-----------------|
| `sample_durations.json` | Per-topic sampling hints: duration, expected Hz, header flags | Auto-updated by `gather.py`; `notes` and `expected_hz` are never overwritten |
| `topic_descriptions.json` | Human-written 3-level topic descriptions | **Never** auto-overwritten; edited manually |

### Generated Files (not committed)

| File | Generated by | Contents |
|------|-------------|----------|
| `docs/artifacts/topic_data.json` | `gather.py` | Raw measurements per topic |
| `docs/artifacts/topic_data_described.json` | `describe.py` | Measurements + descriptions + namespace grouping |
| `docs/artifacts/topic_analysis.md` | `report.py` | Final human-readable report |

## 4. gather.py — Detailed Design

### Discovery

Uses `get_topic_names_and_types()` to enumerate all topics, then `get_publishers_info_by_topic()` and `get_subscriptions_info_by_topic()` to collect node names and QoS profiles.

### QoS Matching

For each topic, if any publisher uses `TRANSIENT_LOCAL` durability, the subscription also uses `TRANSIENT_LOCAL` (to receive latched messages). Otherwise `qos_profile_sensor_data` (BEST_EFFORT, VOLATILE, depth=10) is used. This ensures latched topics like `/map`, `/map_metadata`, and costmap snapshots are always received.

### Parallel Sampling

All subscriptions are created simultaneously using a `MultiThreadedExecutor`. The executor spins for `--max-wait` seconds (default 15). This means the total wall-clock time is bounded regardless of the number of topics.

Callback bookkeeping per topic (thread-safe via `threading.Lock`):
- `count` — number of messages received
- `total_bytes` — sum of serialised message sizes
- `timestamps` — list of receive times for Hz calculation
- `header_stamps` — list of `(send_time, recv_time)` pairs for delay calculation (only for messages with a `std_msgs/Header`)

### Hz Calculation

Computed from the inter-arrival timestamps of received messages:
- Mean, min, max, std-dev of inter-arrival intervals
- Span = last_recv – first_recv
- Only calculated when ≥ 2 messages were received

### Delay Calculation

For any message type that has a `header.stamp` field (discovered via `rosidl_runtime_py.get_message()`), the delay is `recv_time – header.stamp`. Reported as mean/min/max/std-dev in seconds. Topics without a header have `supports_delay: false` and `delay_s: null`.

### Adaptive Duration Hints

After every run, `gather.py` calls `_recommend_duration()` on each topic:

| Measured Hz | Recommended `sample_duration_s` |
|-------------|--------------------------------|
| > 50 Hz | 3 s |
| > 10 Hz | 5 s |
| > 1 Hz | 8 s |
| ≤ 1 Hz or silent | 15 s |

These recommendations are written back to `sample_durations.json`. The `notes` and `expected_hz` fields are never touched.

### Output: `topic_data.json`

## 5. describe.py — Detailed Design

Reads `topic_data.json` and `topic_descriptions.json`. For each topic:

1. Looks up the description entry in the database.
2. Copies `one_liner`, `paragraph`, and `deep_dive` into the topic entry.
3. If no description exists, inserts `"TODO – no description written yet"` placeholders.
4. Computes a `namespace` grouping hint (e.g., `/sigyn/sensors`, `/local_costmap`) used by `report.py` for section grouping.
5. Writes `topic_data_described.json` (same structure as `topic_data.json` plus `description` and `namespace` fields on each entry, plus a top-level `described_at` timestamp).

`topic_descriptions.json` is **never modified** by this step.

## 6. report.py — Detailed Design

### Report Sections

| Section | Contents |
|---------|---------|
| Header | Robot name, hostname, ROS distro, generation time, methodology note |
| Table of Contents | Linked list of all sections and namespace subsections |
| Top 20 by Bandwidth | Table: rank, topic, bandwidth, Hz, avg message size, type |
| Full Summary Table | All topics, one row each: topic, bandwidth, Hz, avg msg, type, publishers (with QoS), subscribers (with QoS), health |
| Topic Details | Grouped by namespace; per-topic: type, metrics table, publishers, subscribers, description (at selected depth) |
| Silent Topics | Topics with publishers but no observed messages (likely event-driven or awaiting a trigger) |
| No-Publisher Topics | Topics with subscribers but no publisher (possible misconfiguration) |

### Health Indicators

| Emoji | Meaning |
|-------|---------|
| 🟢 | Rate is within 80–200% of expected, or no expected rate defined |
| 🟡 | Rate is 50–80% of expected |
| 🔴 | Rate is < 50% of expected |
| 🟠 | Silent — has a registered publisher but zero messages observed |
| ⚪ | No publisher registered |

### Description Depth

Controlled by `--depth`:
- `one_liner` — one sentence in bold; no paragraphs
- `paragraph` — one_liner + the paragraph block
- `deep_dive` (default) — one_liner + paragraph + all deep_dive paragraphs

### No-Publisher Formatting

When a topic has no publishers or no subscribers, the cell renders as:

```html
<span style="color:orange">NONE</span>
```

This renders in most Markdown viewers that support inline HTML (GitHub, VS Code preview, MkDocs).

## 7. sample_durations.json — Schema

```json
{
  "/topic/name": {
    "sample_duration_s": 5,
    "expected_hz": 50.0,
    "has_header": true,
    "supports_delay": true,
    "last_measured_hz": 49.8,
    "last_run": "2025-06-01T10:23:44+00:00",
    "notes": "VL53L0X ToF ranging sensor, front-left forward-facing."
  }
}
```

| Field | Set by | Notes |
|-------|--------|-------|
| `sample_duration_s` | Manual seed + auto-updated by `gather.py` | Minimum recommended sampling duration |
| `expected_hz` | Manual only | Used for health check; never auto-overwritten |
| `has_header` | Manual seed + updated by `gather.py` | Whether the message type has `std_msgs/Header` |
| `supports_delay` | Updated by `gather.py` | Whether delay measurements succeeded at runtime |
| `last_measured_hz` | Updated by `gather.py` | Most recent measured mean Hz |
| `last_run` | Updated by `gather.py` | ISO-8601 timestamp of most recent measurement |
| `notes` | Manual only | Free text; never auto-overwritten |

## 8. topic_descriptions.json — Schema

```json
{
  "/topic/name": {
    "one_liner": "One sentence description.",
    "paragraph": "A short paragraph for a developer reading the code.",
    "deep_dive": "Multiple paragraphs with full context, design rationale, and operational notes."
  }
}
```

All three fields default to `"TODO"` for newly scaffolded topics. The `deep_dive` field may be omitted for simple pass-through topics; `describe.py` treats a missing or `"TODO"` value as absent and does not include it in the report.

## 9. Design Decisions

### Why separate gather / describe / report?

The sampling step takes 15–20 seconds (wall clock) because it must wait for slow topics like `/map` and `/global_costmap/costmap_updates`. Descriptions can be edited and the report regenerated in under 2 seconds. Separating the steps avoids the 15-second wait during iterative report development.

### Why parallel sampling?

Sequential per-topic sampling at 15 seconds per topic would take 30 minutes for 118 topics. Parallel sampling with a shared 15-second window takes the same time regardless of topic count. The trade-off is that all Hz measurements are bounded by `--max-wait`, which is acceptable since typical rates range from 1 Hz to 100 Hz.

### Why adaptive duration hints?

The first run uses conservative 15-second windows for unknown topics. Once a topic's Hz is measured, the recommended window shrinks (e.g., a 100 Hz topic only needs 3 seconds). Over a few runs, the total sampling time can decrease as `sample_durations.json` converges.

The adaptive update does not reduce `sample_duration_s` for topics that are silent (never published) — they retain the 15-second window so they have the maximum chance to emit a message on future runs.

### Why three description levels?

- `one_liner` gives enough context in a dense table without wrapping.
- `paragraph` serves the developer who wants to understand a topic without reading the source code.
- `deep_dive` serves the author writing documentation or a technical book, where design rationale, operational notes, and cross-references are valuable.

The `--depth` flag lets you choose the trade-off between report length and detail.

## 10. Extension Guide

### Adding a new topic

When a new topic appears after a hardware change or software update:

1. Run `python3 gather.py` — the new topic is automatically included.
2. Check the missing-description list: `python3 describe.py 2>&1 | grep Missing`.
3. Add an entry to `topic_descriptions.json` for the new topic.
4. Re-run `describe.py && report.py`.

### Adapting to a different robot

1. Copy the `topic_analysis/` directory to the new robot's scripts folder.
2. Delete or empty `sample_durations.json` and `topic_descriptions.json`.
3. Run `gather.py` — it will populate `sample_durations.json` from live data.
4. Run `describe.py` — it will generate scaffold entries for all missing topics.
5. Fill in descriptions incrementally; the report renders `TODO` for missing entries.

### Adding a new report section

`report.py` is pure Python with no framework dependency. Each section is a sequence of `lines.append(...)` calls. Add your new section by inserting a new block after the existing sections and adding a Table of Contents entry.

### Changing the namespace grouping

`describe.py` assigns a `namespace` to each topic using the `_namespace()` helper. The mapping in `_namespace_title()` in `report.py` maps namespace strings to human-readable section titles. Both functions are small and easy to extend.

## 11. Relationship to *ROS 2 for Mere Mortals*

This system was developed as part of the Sigyn robot codebase, which serves as the primary worked example in the book series. The three-step pipeline illustrates several patterns that appear throughout the books:

- **ROS 2 introspection APIs** — `get_topic_names_and_types()`, endpoint info, QoS profiles
- **Message type reflection** — using `rosidl_runtime_py.get_message()` to inspect field structure at runtime
- **QoS matching** — detecting TRANSIENT_LOCAL publishers and adapting subscriber QoS accordingly
- **MultiThreadedExecutor** — processing callbacks from 100+ topics without sequential bottlenecks
- **Separation of concerns** — decoupling live ROS interaction from data processing and report generation

The `topic_analysis.md` output is intended to be committed alongside the source code as living documentation, updated whenever the topic architecture changes significantly.
